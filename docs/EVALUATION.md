# Evaluating Council Against the Generalist Baseline

V1 uses human comparison to determine whether the additional Council structure
creates decision value worth its latency and cost. The comparison is not an
automatic leaderboard and the system does not infer human scores.

## Fair comparison contract

For `both` mode, the CLI builds one `ContextBundle`. Council and Generalist
receive:

- the exact same canonical feature text;
- the exact same repository identity and tracked-working-tree state;
- the exact same evidence manifest and context contents.

The Generalist cannot see specialist, Evidence Resolver, Producer, or Director outputs,
including any Resolver supplemental evidence. Before a
comparison record is accepted, the system verifies feature and context
identity, including hashes and the evidence manifest. This isolates the
evaluation as much as practical: the primary treatment is structured Council
reasoning versus one end-to-end Generalist response.

## Human rubric

The reviewer gives each output an integer score from 1 (weak) to 5 (strong) on
all eight dimensions:

| Dimension | What to assess |
| --- | --- |
| Grounding | Are repository claims supported by supplied evidence, with important unknowns stated rather than invented? |
| Scope reduction | Does the proposal remove work that is unnecessary to test the riskiest assumption? |
| Hypothesis quality | Is the player or product hypothesis specific, causal, and testable? |
| Experiment credibility | Could the proposed test generate interpretable evidence with suitable controls and guardrails? |
| Measurement-to-learning logic | Do signals and validity checks lead coherently to scale, iterate, kill, or need-more-data conditions? |
| Technical realism | Does the proposal reuse supported capabilities, expose missing evidence, and estimate implementation honestly? |
| Decision usefulness | Does the output help a Product/Director reviewer make and explain a practical next decision? |
| Conciseness | Is the useful reasoning presented without avoidable repetition or noise? |

The reviewer must then choose `Generalist`, `Council`, or `Tie` and provide a
non-empty, human-written reason. Scores are never inferred, copied from model
confidence, or generated by another model.

## What additional Council value looks like

Council earns its extra calls when the specialist decomposition reveals
materially useful tensions that an end-to-end answer obscures—for example,
when player value, technical authority, measurement validity, reversibility,
and scope constraints pull in different directions. Producer should reconcile
shared conclusions while retaining genuine disagreements; Director should turn
that evidence into a clearer decision and smaller credible test.

More text is not evidence of more value. Council should win because its
grounding, uncertainty handling, scope reduction, experiment validity, or
decision usefulness is better—not because it has more sections.

## When the Generalist may win

The Generalist may be preferable when the feature is straightforward, the
evidence is unambiguous, and specialist decomposition adds repetition without
changing the decision. It may also win when lower latency, fewer calls, lower
cost, or greater conciseness matters more than the Council's added explanation.
A tie is valid when both outputs are equally useful after those tradeoffs.

## Telemetry and cost

Persisted execution telemetry records model, duration, input tokens, output
tokens, and total tokens by role. Council nominally uses six calls, Generalist
one, and `both` seven. Local cost estimates use a dated pricing snapshot and
report unpriced models rather than inventing a price.

Latency, tokens, and cost should be reported alongside the human rubric, but
they do not replace it. Preflight numbers are deterministic approximations;
persisted SDK usage is the authoritative token record for the completed run,
and cost remains an estimate derived from that usage and the snapshot.

## Interpreting the feature experiment

Evaluation of answer quality is separate from interpretation of the proposed
feature experiment. Both Council and Generalist must apply validity precedence:

| Experiment result | Interpretation |
| --- | --- |
| Valid positive evidence | Scale |
| Valid evidence that is useful but calls for a change | Iterate |
| Credible negative evidence from a valid experiment | Kill |
| Assignment, persistence, eligibility, implementation, or instrumentation makes the result uninterpretable | Need more data |

A broken experiment is not trustworthy negative product evidence. Numeric
thresholds must come from the feature brief, grounded repository evidence, or
a human decision; the evaluator must not reward invented precision.

## Product/Director human decision

The Director output is an AI recommendation, not authority to proceed. The
human reviewer records one action:

- **Accept:** adopt the Director recommendation.
- **Reject:** decline it without substituting another Director decision.
- **Modify:** record a different allowed Director decision.

An optional note can preserve the rationale. Original Director questions and
JSON remain unchanged for traceability; once the human decision exists, the
report presents those questions as resolved by that decision. Completed review
records cannot be silently replaced.

## Recommended validation process

1. Run `--dry-run` and inspect repository identity, context size, selected
   evidence, models, expected calls, and conservative cost.
2. Confirm the selected source may be sent to the configured provider and give
   explicit consent.
3. Run `--mode both` so one context is shared by Council and Generalist.
4. Inspect both outputs for unsupported repository claims before judging
   recommendation quality.
5. Review experiment validity, effort semantics, disagreements, smallest
   experiment, and decision conditions.
6. Record the Product/Director accept, reject, or modify decision.
7. Independently score every rubric dimension, select an overall preference,
   and write the reason.
8. Compare latency, tokens, and estimated cost with the human value judgment.
9. Treat one feature as a case study, not a general performance conclusion;
   repeat across materially different feature classes before changing the
   architecture.

The offline command can complete pending review without rerunning models:

```text
python -m council review --run RUN_ID [--output-dir PATH]
```
